# iOS code map: the Rust side

## Rust (`src-tauri/`)

### How the code is kept apart

- `tauri-build` sets `cfg(desktop)` or `cfg(mobile)` automatically for the target platform. Mark all desktop-only code with `#[cfg(desktop)]` and all iOS-only code with `#[cfg(mobile)]`. Code without a mark is shared.
- **Checked on every Rust change:** CI's Linux `native` job runs Android's `cargo clippy` with warnings as errors, so desktop-only code left ungated (dead on the phone) or a dependency given to the desktop alone fails the pull request. Code gated `target_os = "ios"` (or `not(target_os = "ios")`) is compiled only by the full suite's `ios` job, which doesn't block: run `cargo check --target aarch64-apple-ios-sim --lib` before a pull request that touches it.
- **Dependencies:** `tauri-plugin-updater` and `tauri-plugin-process` are under `[target.'cfg(not(any(target_os = "ios", target_os = "android")))'.dependencies]` in `Cargo.toml` (the metadata of both plugins lists iOS support as none). `tauri-plugin-single-instance` was already included only on Windows/Linux. Tauri's `tray-icon` feature (background mode) is on for every target, but Tauri builds no tray for iOS. The macOS PDF dependencies (objc2-\*) and the Windows/Linux webview dependencies were already split by OS. `opener` and `dialog` support iOS and stay shared. The document parsers `pdf-extract`, `calamine`, `zip`, `quick-xml`, `dom_query`, `encoding_rs` and `codepage` (`src/extract/`: chat attachments and the AI's project tools) are pure Rust, so they are shared too.
- **Command registration:** `invoke_handler.rs` has the single `invoke_handler` list. Shared commands are in the first half of the `generate_handler!` list. Desktop commands are in the second half, each with `#[cfg(desktop)]` in front of it (tauri-macros supports attributes on single commands). So on iOS these commands are never registered.
- **Builder:** The shared part is in `run()`: the opener and dialog plugins, `PendingOpenPaths`, and the state the plugin commands read (`PendingUris`, `PluginAiTools`, `MetadataIndex`). The desktop part is in `desktop_builder()`: the updater/process plugins, the state for windows, dragging, sessions and the chat window, background mode and MCP, `on_window_event`, and `setup` (argv, session restore, CLI, menu bar, window size).
- **State and commands go together:** a command registered for every platform may only read state managed in the shared part. `app.state::<T>()` for a `T` that only `desktop_builder()` manages panics, and on iOS that aborts the app the moment the page makes the call (1.3.0's first TestFlight build closed at launch this way). Use `try_state` where the state is desktop-only on purpose. `scripts/smoke-ios-sim.sh` starts the simulator build as a returning user and fails if the app is gone 20 seconds later; CI's `ios` job runs it after the build.
- **Permissions (capabilities):** `capabilities/default.json` is shared and contains core, opener, dialog and event. `capabilities/desktop.json` is limited to desktop with `"platforms": ["linux","macOS","windows"]`. It holds the permissions for window chrome, full screen, always-on-top, the title, and updater/process. Without this split, the iOS build fails because it cannot find `updater:default`.
- **Configuration:** `tauri.conf.json` adds `bundle.iOS.minimumSystemVersion = "16.4"`. `tauri.ios.conf.json` is merged into the iOS configuration and does two things:
  1. It keeps only one main window, without the desktop window options, and marks it `"create": false` as on the other platforms. (When Tauri merges, it replaces the whole `windows` array, so every platform config that has `windows` must include this.) `build_main_window` in `editor_windows.rs` creates the window after settings are loaded, so the iOS webview also gets the boot script (see [Settings and UI state](#settings-and-ui-state) below).
  2. It sets `createUpdaterArtifacts: false`.

  Do not turn off `macOSPrivateApi` in the iOS config. If you do, the CLI rewrites the tauri features in `Cargo.toml`.
